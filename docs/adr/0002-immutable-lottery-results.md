# ADR-0002：抽奖按开奖时刻判定资格，结果不可修改

- **状态**：已采用
- **日期**：2026-11-09（按当前代码重写）

## 背景

抽奖会在设定的时间自动开奖，但 worker 每 30 秒才运行一轮，真正开奖的时刻可能比设定时间晚一些。

在这段时间里，参与者的情况可能已经变了：账号可能被停用，身份可能从正式成员变成朋友，月度签到的天数也可能增加。如果按"处理时的状态"来判断谁有资格，结果就会受处理快慢影响，显得不公平。

另外，抽奖结果一旦公布，就不能再被修改或重抽。

## 决定

1. **资格看历史记录，不看当前状态**
   - 账号状态、身份、签到这些会影响资格的变化，都会写进只能追加、不能修改的历史记录表，例如 `LotteryAccountFact`。
   - 开奖时，读取"设定开奖时刻"那一刻的状态来判断资格，不用开奖处理那一刻的状态。
   - 如果那个时刻的记录不完整，就拒绝开奖，等下一轮再处理。

2. **开奖只进行一次**
   - worker 在事务里依次完成：加锁 → 重新读取抽奖数据 → 生成资格快照 → 抽取（使用 `node:crypto` 的随机数）→ 写入结果，并把状态改为已开奖（DRAWN）。
   - 如果抽奖已经不是"进行中"，直接返回已有的结果，不会再抽一次。

3. **数据库层面禁止修改**
   - 触发器 `Lottery_immutable` 禁止修改已发布抽奖的参数，也禁止修改已开奖的结果。
   - 唯一允许的变更是超级管理员的"违规删除"标记。

4. **先提交结果，再发通知**
   - 开奖结果所在的事务提交之后，才单独生成通知。
   - 通知生成失败时，不会回滚、也不会重抽。下一轮会给"已开奖但还没有通知"的抽奖补发通知。
   - 通知按 eventKey 去重，补发不会产生重复通知。
   - 目前抽奖结果只发站内消息，对外推送仍处于模拟状态。

## 后果

- **好处**：
  - 开奖结果与 worker 处理的快慢无关，可以复查。
  - 结果从数据库层面就改不了。
  - 通知出问题不会影响结果本身。
- **代价**：
  - 资格历史表会一直增长。
  - 开奖时需要短暂锁住账号表（`lottery_try_account_fence`，拿不到锁就立即放弃），没拿到锁就等下一轮。
- **以后改动时要注意**：
  - 下面这些改动会直接影响公平性，必须按高风险变更处理：修改资格的判定时刻、删除历史记录、调整抽取顺序或随机数来源、允许修改已开奖的结果。
  - 以"优化查询性能"为理由去改这些地方是不可以的。
