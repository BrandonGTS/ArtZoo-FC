# ADR-0004：恢复备份后，用离线重新登记恢复媒体文件身份

- **状态**：已采用
- **日期**：2026-11-15

## 背景

开启上传配额后，网站要保证"删掉的正是当初上传并记过账的那个文件"，否则可能误删别的文件，或者把配额退错。为此数据库给每个磁盘文件（`MediaStoredComponent`）保存一个身份指纹 `storageIdentityFingerprint`，三个媒体根目录整体另有一个基线指纹 `MediaBudgetState.baselineFingerprint`。

身份指纹不只看内容，还包含文件和所在目录在磁盘上的**物理身份**：设备号（dev）、inode、属主，再加上根目录路径、对象 UUID、部件名、原内容哈希和上传批次 `generation`（计算在 `packages/media/src/stock-bound-io.ts`）。这样即使有人把文件换成一个内容完全相同的副本，网站也能发现。

问题是：从备份恢复时，文件是重新解包写出来的，inode 全都变了；挂载方式变化也可能改变设备号。内容一点没变，身份比较却会失败，于是删图和退配额都会被拒绝。

## 决定

采用"方案 1：显式的离线重新登记"，身份的计算公式保持不变。

1. 提供维护命令 `media-reregister`：
   - 停止 web、worker，先做一份 `register-*` 备份；
   - 用只读挂载逐个读取当前仍占用磁盘的文件，核对内容哈希和计费字节数与数据库原记录一致；
   - 全部通过后，在**一个数据库事务**里把这些文件的身份指纹和基线指纹更新成新的物理身份；提交前再核对一遍，任何变化都整体回滚；
   - 提交后运行独立的只读诊断 `media-identity`，全部一致才按原来的状态开站。
2. `restore`（原地恢复）和 `rollback`（回退）恢复媒体后一律保持停站，并写入 `deploy/media-registration.pending`。标记存在时，`start`、`upgrade`、`rollback`、备份（含定时备份）和 Windows 入口的 `-start` 都会拒绝，直到登记成功。
3. 已经完成删除并退还配额的历史记录（删除意图为 `ACKNOWLEDGED` 且有退额记录）原样保留：不要求文件重新出现，也不重复退额。

## 不能做的事

以后改相关代码时，下面这些也不能做：

- 不用磁盘上现算的哈希覆盖数据库里的原内容哈希；不重建空基线；不清零或重算配额。
- 不在网站启动时自动"修复"身份。身份检查和登记只在站长显式执行维护命令时发生。
- 遇到下列情况整体拒绝，不跳过、不部分提交：文件缺失或内容不符；符号链接、硬链接或特殊文件；目录属主或权限不可信；类型未知或缺少内容证明的记录；非零的基线汇总记录；还没完成的删除意图（包括 `PREPARED`）；删除意图和退额记录互相矛盾。
- 单次登记的上限是 10000 个文件组件、10 GB 计费字节、事务 240 秒（每页 128 行）。超过就报错，不分批提交。

## 考虑过的替代方案

**方案 2：长期身份只记逻辑信息，物理身份只在单次操作内比较。** 长期指纹去掉 dev 和 inode，只绑定根路径、文件名、原内容哈希和批次。

- 好处：恢复备份或换挂载后不用再登记。
- 代价：两次操作之间把文件换成同内容的副本会被接受，安全保证变弱；需要新增"算法版本"列和迁移；估计产品代码 500–900 行，另需约 700–1000 行脚本和测试代码。

目前不采用。以后如果恢复太频繁、登记的停站时间太长，可以重新评估。

## 后果

- **好处**：保留了"删的就是当初那个文件"的严格保证；身份算法和数据库结构都没有变。
- **代价**：每次恢复（包括回退）都要多一次停站登记。登记要把所有媒体完整读两遍，媒体越多停站越久。
- **已知限制**：
  - 登记只是在维护期间按原内容重新建立信任，发现不了维护之前就已经被换成同内容副本的文件。
  - 数据库事务管不到磁盘。提交结果不确定（进程被杀、连接中断）时保持停站，重新做只读检查，不猜测结果。
  - 现场如果留有没做完的删除（例如删图做到一半），登记会拒绝。这时需要另行设计"承接未完成删除"的处理，不能删记录绕过。
- **运维**：启动入口不自动检查身份（站长 2026-11-16 实测，家庭 Server 在 Windows 重启后身份保持一致）。怀疑身份有变化时，先运行只读的 `media-identity`，退出码为 2 再登记。操作步骤见 DEPLOYMENT.md。
