# ADR-0001：在 PostgreSQL 事务内协调并发

- **状态**：已采用
- **日期**：2026-11-09（按当前代码重写）

## 背景

网站进程（web）和后台进程（worker）是两个独立的进程，会同时修改同一批数据，比如活动、积分、抽奖、通知。

如果只在单个 Node 进程里加锁，管不到另一个进程，所以协调必须放在两边都能访问的地方。

## 决定

不引入 Redis 或专门的任务队列，并发协调全部在 PostgreSQL 里完成：

1. **事务**：写操作统一用 `ReadCommitted` 隔离级别。业务数据和它产生的副作用意图（站内消息、QQ 通知排队等）写在同一个事务里，一起提交，或者一起回滚。
2. **咨询锁**：对同一个对象的修改，用 `pg_advisory_xact_lock` 串行执行，锁名形如 `activity:<id>`。只读路径使用共享锁 `pg_advisory_xact_lock_shared`。锁在事务结束时自动释放。
3. **行锁**：需要锁住某个账号时，使用 `SELECT ... FOR NO KEY UPDATE`。积分更新就是这样做的。
4. **数据库约束兜底**：唯一性、归属关系、不可修改这类规则，同时写成数据库约束或触发器（见 ARCHITECTURE"只写在迁移 SQL 里的规则"）。这样即使代码有疏漏，也写不进错误数据。
5. **加锁后重新检查**：拿到锁之后，重新读取数据，重新检查会话、权限、截止时间和版本号。加锁之前读到的结论不能直接拿来用。

## 后果

- **好处**：
  - 只依赖一个数据库，部署简单。
  - 业务状态和通知意图是原子写入的，不会出现"报名成功了但通知丢了"的情况。
  - 多个 worker 同时运行也是安全的。
- **代价**：
  - 热门对象上会有锁等待。
  - 长事务会占用连接。为此设置了等锁超时 10 秒、单条语句超时 15 秒。
  - 部分维护任务需要更粗粒度的锁，例如抽奖开奖时会短暂锁住账号表。
- **以后改动时要注意**：
  - 锁是一种业务约定。修改锁的名字、把独占锁改成共享锁、调整加锁的先后顺序，都可能影响其他请求，甚至造成死锁。
  - 自动重试（`transaction-retry.ts`）只能用于确认可以安全重放的事务。带外部副作用的事务不能重试，比如发短信。
